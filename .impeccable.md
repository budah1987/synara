## Design Context

### Users

Synara is for developers and technical operators who move between several repositories, worktrees, terminals, and AI conversations throughout the day. They already understand Git, but the product should remove repository setup and worktree bookkeeping from their normal flow so they can stay focused on the work itself.

### Brand Personality

Clean, subtle, and usable. Synara should feel focused, restrained, and dependable: dense enough for expert use, calm enough to scan quickly, and explicit when an action can change Git state.

### Aesthetic Direction

Keep Synara's existing native desktop character, compact chrome, and current light and dark themes. Use Conductor as a hierarchy and interaction reference rather than a visual template. Workspace names are primary navigation labels; branch names, paths, remotes, and pull-request metadata are supporting information revealed on demand.

### Design Principles

1. **One sidebar row represents one worktree.** Conversations belong to that workspace and appear as tabs in the main panel.
2. **Preserve the user's words.** A workspace title stays readable and stable even when its branch or filesystem path is long.
3. **Use progressive disclosure for Git details.** Keep actionable status visible, but move branch, path, remote, source, and pull-request metadata into accessible hover and focus details.
4. **Make repository setup part of the product.** A user can add a local folder or connect a GitHub repository, then create a workspace from a target branch, existing branch, or pull request without manually cloning and wiring it first.
5. **Keep display identity separate from Git identity.** Renaming a workspace is always safe and immediate; renaming its branch is an explicit, validated Git operation with clear remote consequences.
6. **Let motion explain state.** Use brief opacity and transform transitions for disclosure, tabs, and progress, respect reduced-motion preferences, and avoid decorative animation.
7. **Prefer durable server-owned mutations.** Clone, fetch, worktree creation, and branch rename operations must be resumable or recoverable and expose useful failure states to the UI.
